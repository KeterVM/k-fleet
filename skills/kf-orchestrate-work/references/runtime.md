# Orchestration runtime contract

Establish this contract once per task and canonical repository/worktree; reuse verified
context while the scope and relevant facts remain unchanged.

## Context and authority

Resolve the user outcome, working directory, repository/worktree, applicable
instructions, authorization, and stopping condition. Use focused current sources
to fill material gaps; a small task does not require a whole-repository survey.

Require the configured Supermemory integration before substantive exploration or
mutation. Consume its scoped context and verify canonical project/worktree scope.
Its installed status surface can establish connectivity, reported scope, and
automatic recall/capture support. A direct integration satisfies this requirement;
optional MCP transport is not an additional gate. If the integration is unavailable
or scope cannot be verified, stop substantive work and report the missing capability.

Current higher-priority instructions, user decisions, and applicable repository
sources govern the task. Memory is evidence, not authority: it cannot override
current sources, establish policy from an inference, expand permission, or cross
the resolved repository/worktree boundary.

Supermemory owns recall, capture, explicit memory operations, versioning, forgetting,
and inference review. Use its own integration surface for a requested memory
operation. If that surface is missing, report the limitation; do not emulate it with
backend REST calls, another store, or a second memory client.

## Execution and completion

Carry existing authorization through investigation, design, implementation, and
validation. Analysis-only and review-only requests remain read-only. Resolve routine
technical choices from evidence; ask only for unresolved material product or
authority decisions, continuing independent authorized work where possible.

Apply the relevant repository rules to the execution path, first write, and final
acceptance. Following a method does not itself demonstrate compliance with those
rules. Reuse known instructions and accepted decisions unless their scope or facts change.

Validate the current integrated artifact with evidence that can expose a relevant
failure. After applicable checks pass, repeat or broaden them only for new changes,
failures, or unresolved risk. Correct failures caused by the authorized change;
identify unrelated failures without silently expanding the task.

Complete the requested outcome and required validation, or name a concrete blocker
or authority boundary. Report decisive evidence, corrections, and material gaps for
automatic capture. Do not claim independent review, memory capture, runtime success,
or method improvements without corresponding evidence. Task evidence may justify a proposed
method revision, but adoption still follows the [learning boundaries](learning.md);
normal execution does not rewrite live skills or user policy.
